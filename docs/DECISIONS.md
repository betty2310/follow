# Product & Technical Decisions

Settled during the initial design interview (2026-09-30). Change these only with the owner's agreement; record changes here with a date.

## Context

- Single user: a teacher who mentors ~30 students, each building their own project.
- Each student has **one in-person 1:1 session per week**, **5–10 minutes**, in **Vietnamese** (with English tech terms mixed in).
- The teacher wants each session recorded, transcribed, summarized, and a simple view of who reported each week.
- Owner and students consent to cloud processing of the audio. Privacy is not a design constraint.

## Decisions

| # | Topic | Decision |
|---|---|---|
| D1 | Platform | Native macOS app, macOS 26+, Apple Silicon. Personal tool, **not** Mac App Store, **no sandbox**. |
| D2 | Stack | Swift 6, SwiftUI, **GRDB (SQLite)** (see D19). Xcode project generated by **XcodeGen** from `project.yml` (never hand-edit `.xcodeproj`). |
| D3 | UI language | **English** UI. Generated summaries are in **Vietnamese**. |
| D4 | Engines are pluggable | Transcription and summarization each sit behind a protocol (`TranscriptionEngine`, `SummarizationEngine`). Swapping providers must not touch views or models. |
| D5 | Transcription (STT) | Cloud STT with **speaker diarization**. Default **Soniox** (async). Also implement **Gemini 3.5 Transcribe** and **Deepgram Nova-3**. See research below. |
| D6 | STT comparison mode | The app can run one recording through several STT engines and show the transcripts side by side so the teacher can choose the best one on real audio. |
| D7 | Summarization | Shell out to **`claude -p`** (Claude Code CLI, the owner's subscription) with model **Sonnet**. CLI path + model configurable in Settings. |
| D8 | Speaker roles | STT returns anonymous speakers (A/B). The summarizer **infers Teacher vs Student from context**. The UI has a **swap** button to fix mistakes. Better classification (e.g. voice enrollment) is future work. |
| D9 | Summary format | Free-form Vietnamese markdown using a fixed template (below). **Editable**. The labeled transcript is kept next to it. **No** structured action items or checklists: the teacher reads last week's summary before the next session. |
| D10 | Students | Imported from an **Excel (.xlsx)** file into a **Group** (see D20). Fields: Student ID (MSSV) + Full name **required**; Class, Project title, Email optional. Real-world example header (HUST): `Mã số SV/HV \| Họ tên SV/HV \| Email`.  |
| D11 | Weeks | **Calendar weeks (Mon–Sun)**. Multiple sessions in the same week are allowed. |
| D12 | Recording | Pick a student → Record → Stop → processing runs in the background (the teacher can record the next student). Audio kept locally as `.m4a`. Also: **import an audio file** and **re-run** processing. |
| D13 | Progress tracking (revised 2026-09-30 by D26) | Keep it simple: a group view of who reported, plus a per-student **timeline** of weekly summaries. |
| D14 | Storage (revised 2026-10-04 by D31) | Visible folder `~/Documents/ProjectRecord/`: `ProjectRecord.sqlite` + audio at `audio/<group>/<MSSV>/<yyyy-MM-dd_HHmm>.m4a`. API keys in **UserDefaults** (D31). |
| D15 | Export | **Not in v1.** |
| D16 | Name | **ProjectRecord**. |
| D17 | Layout (2026-09-30, revised 2026-09-30 by D25, D26) | Single window, `NavigationSplitView`. Sidebar: **search box** on top → **Groups** → **Archived**: every group is a collapsible row with its students under it; selecting a group shows its **dashboard**. Detail pane shows the selected item. Settings are only in the Settings window (⌘,). |

| D18 | Import UX (2026-09-30) | Import is a sheet: it shows **instructions** (required and optional fields), then after the file is picked, **column mapping** (one picker per field, auto-guessed from headers by exact then partial match), a *first row is header* toggle, the target **group** (existing or new), and a **preview** with new/updated counts. Import is enabled only when the required fields are mapped. First worksheet only. |
| D19 | Database (2026-09-30) | **GRDB over SQLite** replaces SwiftData. All DB access goes through `AppDatabase` (schema via versioned migrations, reads via `ValueObservation`, writes via methods). Records are plain structs. |
| D20 | Groups (2026-09-30) | Data model is **Group → Students → Sessions**. A *group* is a folder of students the teacher organizes (replaces "Term"). *Project* always means the **student's own project** (`projectTitle`). Import targets an existing or new group; into an existing group it **adds new MSSVs and updates existing ones, never deletes**. Same MSSV in two groups = two separate students. |
| D21 | Name normalization (2026-09-30) | On import only: Unicode NFC, trim, collapse spaces, capitalize the first letter of each word (`NGUYỄN HÀ ANH` → `Nguyễn Hà Anh`). MSSV is trimmed; email is trimmed and lowercased. |
| D22 | Time format (2026-09-30) | Dates in SQLite are readable **local time with UTC offset**: `2026-09-30 10:37:39.175+07:00` (`DBTimestamp`). **No epoch numbers, no bare UTC.** Durations and offsets inside a recording (utterance `start`/`end`) are **seconds** (`12.5`). |
| D23 | Student page (2026-09-30) | The student page shows a **week calendar strip** on top (one column per Mon–Sun week, from the oldest session or at least 8 weeks back through this week; each session is an entry in its week's column, colored by status). Clicking an entry shows that session **below**: status and actions (Show in Finder, Re-run), the summary, and the transcript labeled Teacher/Student with a swap button. The newest session is selected by default. |
| D24 | Calendar views (2026-09-30) | The student calendar has a **Week / Month** switch (remembered between launches). *Week* is the D23 strip of week columns; *Month* is a Mon–Sun day grid for one month with ‹ Today › navigation, sessions shown as chips in their day. **Built in-house** (~150 lines on `WeekCalendar`), not with a calendar library: the libraries reviewed (iletai/SwiftUICalendarView, Mijick/CalendarView, Chiji1108/swiftui-calendar) are mostly features we don't need and would still require custom cells. |
| D25 | Group management (2026-09-30) | Right-click in the sidebar: on a group → **Rename…**, **Import Students into Group…**, **Archive / Unarchive**, **Delete…**, **New Group…**; on empty space → **New Group…**, **Import Students…**. **Archive** only moves the group to a collapsed *Archived* section (`studentGroup.archivedAt`), nothing is deleted. **Delete** asks for confirmation (shows student/session counts, offers *Archive Instead*), deletes students and sessions, and moves recordings to the **Trash**. Each group's students can be hidden (see D26); a toolbar button hides/shows students in all groups. Collapsed state is remembered. |
| D26 | Sidebar & group dashboard (2026-09-30) | **No Settings row** in the sidebar (⌘, only); the sidebar has just the *Groups* and *Archived* sections. Groups have **no disclosure arrow**: the folder icon shows the state (filled = students shown, outline = hidden) and **double-clicking** a group toggles it. The group dashboard keeps the this-week tiles and not-reported list, and replaces the students × weeks grid with the **D24 calendar** (Week / Month), where each day shows **how many students reported** that day (a student counts once per day). |
| D27 | CI/CD (2026-10-01, revised 2026-10-04 by D28, D30) | GitHub Actions on `macos-26`: **PR** → `make test`; **push to `main`** → test + Release build, zip kept as a workflow artifact; **tag `v*`** → test + build + **GitHub Release** with `ProjectRecord-<version>.zip`. Version comes from the tag (`v1.2.0` → `MARKETING_VERSION=1.2.0`); the build number is the version too (D28). The app is **not notarized** (no Apple Developer account; signing: D30); users clear the quarantine flag once (`xattr -dr com.apple.quarantine`). |
| D28 | In-app updates (2026-10-04) | **Sparkle 2** (SPM, `AppUpdater`), not a home-made GitHub API check. Feed: `appcast.xml` attached to every GitHub Release, read from `releases/latest/download/appcast.xml`; the release workflow writes it with `generate_appcast` and signs the zip with an **EdDSA key** (public half `SUPublicEDKey` in `project.yml`, private half the repo secret `SPARKLE_PRIVATE_KEY` and the owner's login Keychain). EdDSA is what lets builds without an Apple certificate update each other, and Sparkle clears the quarantine flag itself. Checks **at every launch and daily**. An update found at launch opens Sparkle's window (*Install* / *Skip This Version* / *Remind Me Later*); one found later only turns the **version label at the bottom of the sidebar** into a *New version x.y.z* bubble, so it never interrupts a session; clicking it opens the window. *Skip* hides the bubble. Also **ProjectRecord → Check for Updates…** and a daily-check toggle in Settings. The update window shows commit subjects since the previous tag. `CFBundleVersion` = the tag's version, so Sparkle orders releases by tag. Debug builds never check on their own. |
| D29 | Session edit, delete & notes (2026-10-04) | The **project title** belongs to the student (`student.projectTitle`), shown as the student page's **heading** (*No title* when empty) with a small pencil to edit it in place. Each session has a free-text **note**, not used by the transcription/summary pipeline: *Add Note* when there is none; otherwise the text with small **Edit** and **Delete** buttons (delete asks first). Editing shows a text box with Cancel / Save (⌘↩). **Edit…** (session header or right-click a calendar chip) opens a sheet for the date and the summary markdown (summary locked while the pipeline runs). **Delete…** asks for confirmation, deletes the session, and moves its recording to the **Trash**; not allowed while recording. A **Notes** toolbar toggle on the student page opens an inspector listing every session's note (newest first); clicking one selects that session. |
| D30 | Code signing (2026-10-04) | Release builds are signed with a **self-signed certificate** `ProjectRecord Self-Signed` (RSA 2048, code signing only, valid until 2046), not ad-hoc. Ad-hoc identity is the binary's hash, so every update looked like a new app to macOS and lost the Microphone/Documents permissions; with a certificate the designated requirement is `identifier "dev.betty.ProjectRecord" and certificate leaf = H"409a8c16…"`, the same for every build, so permissions carry over. `make release` re-signs the outer app after Xcode's ad-hoc build (`SIGN_ID`, `-` = ad-hoc). The certificate lives in the owner's login Keychain and, for CI, in the secrets `SIGNING_CERT_P12` (base64) and `SIGNING_CERT_PASSWORD`; the release workflow imports it into a throwaway keychain. Main-branch builds stay ad-hoc. Gatekeeper still doesn't trust it, so first installs still need the `xattr` step. **Keep the certificate:** a new one changes the identity and every user is asked for permissions once more. A Developer ID ($99/year) would also remove the `xattr` step; not worth it for now. |
| D31 | API key storage (2026-10-04) | API keys live in **UserDefaults** (`APIKeys`, plist `~/Library/Preferences/dev.betty.ProjectRecord.plist`), not Keychain. The app has no Apple team ID, so Keychain items are tied to the code signature and macOS asked for the login password whenever Settings or a recording read a key. It's a personal app, so a readable plist is fine. On first launch, keys saved by older builds are moved out of Keychain once (`APIKeys.migrateFromKeychain`, may ask for the password one last time). Keys are still never committed. |

## STT research (Sept 2026, for ~1,300 min/month)

| Provider | VI + diarization | ~Cost/month | Notes |
|---|---|---|---|
| Soniox (async) | ✅ / ✅ | ~$2 | Best VI WER in vendor benchmark; upload → create → poll |
| Gemini 3.5 Transcribe (preview) | ✅ / ✅ | ~$6.50 | Single call, custom vocabulary (≤1000 terms), ≤30 min/request |
| Deepgram Nova-3 | ✅ / ✅ | ~$6–7 | Single sync POST, $200 free credit |
| AssemblyAI | ✅ / ✅ | ~$3–5 | Upload → poll |
| OpenAI gpt-4o-transcribe-diarize | ✅ / ✅ | ~$8 | Weakest VI in benchmark; no prompt/keyterms |
| Google Chirp 3 | ✅ / ❌ | – | No VI diarization, ruled out |

WER numbers came from Soniox's own comparison pages. **Verify on real recordings with the comparison mode (D6).**

Sources: soniox.com/pricing, soniox.com/docs, ai.google.dev/gemini-api/docs/models/gemini-3.5-transcribe, developers.deepgram.com, deepgram.com/pricing.
